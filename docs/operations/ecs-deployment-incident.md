# ECS Deployment Incident Report

## 1. 概要

GitHub ActionsからAmazon ECSへアプリケーションをデプロイした際、Application Load Balancer（ALB）のヘルスチェックに関連する問題により、ECSタスクが停止し、デプロイが失敗した。

初回調査では、同じタスク定義を使用した手動再デプロイによって復旧できたものの、根本原因は特定できなかった。

その後、同様の障害が再発したため、ECSサービスイベントとALBヘルスチェックログを時系列で照合した。

調査の結果、ALBのHealthy判定に必要な連続成功回数が、アプリケーション起動時の挙動と組み合わさり、デプロイ失敗に関係していた可能性が高いと判断した。

Terraformの設定を変更し、AWS環境の再構築とGitHub Actionsからの連続デプロイによって改善を確認した。

## 2. 対象環境

| 項目                                | 内容                           |
| ----------------------------------- | ------------------------------ |
| アプリケーション                    | Equipment Inspection System    |
| アプリケーション基盤                | Java / Spring Boot             |
| 実行環境                            | Amazon ECS / AWS Fargate       |
| ロードバランサー                    | Application Load Balancer      |
| デプロイ                            | GitHub Actions                 |
| コンテナポート                      | 8080                           |

| ヘルスチェック間隔                  | 30秒                           |
| ヘルスチェックタイムアウト          | 5秒                            |
| Healthy判定の連続成功回数（変更前） | 5回                            |
| Healthy判定の連続成功回数（変更後） | 2回                            |

| ECSデプロイ                         | Circuit Breaker / Rollback有効 |

## 3. 発生事象

### 3.1 初回障害（タスク定義rev15）

GitHub Actionsから新しいタスク定義 `equipment-inspection-task:15` を使用したデプロイを実施した。

初回デプロイではECSタスクが停止し、サービスは以前のタスク定義 `:14` にロールバックした。

ALBヘルスチェックログでは、初期段階の `ConnectionReset` と、その後のHTTP `200 PASS` を確認した。

同じタスク定義 `:15` を使用した手動再デプロイでは、ECSサービスが安定状態となり、ALBターゲットがHealthyになった。

また、`https://kdevnest.com/login` へのHTTPリクエストで `200` を確認した。

ただし、この時点ではGitHub Actionsからの再デプロイ成功は確認できず、根本原因は未確定だった。

### 3.2 再発障害（タスク定義rev20）

その後、GitHub Actionsによるデプロイで同様の問題が再発した。

新しいタスク定義 `:20` を使用したデプロイでは、ECSタスクがALBヘルスチェック失敗によって停止し、以前のタスク定義 `:19` へロールバックした。

GitHub Actionsでは、ECSサービスの安定化待機がタイムアウトした。

## 4. 調査内容

### 4.1 調査対象

以下の情報を確認した。

- ECSサービスイベント
- ECSタスクの起動・停止時刻
- ECSタスク停止理由
- ALBヘルスチェックログ（Amazon S3）
- ALBターゲットグループのヘルスチェック設定
- ECSサービスのヘルスチェック猶予期間

### 4.2 ALBヘルスチェックログ

タスク定義rev20のタスク（プライベートIP `10.0.2.185`）について、以下の結果を確認した。

| 時刻（JST） | ヘルスチェック結果     |
| ----------- | ---------------------- |
| 14:52:55    | FAIL / ConnectionReset |
| 14:53:25    | FAIL / ConnectionReset |
| 14:53:55    | PASS / HTTP 200        |
| 14:54:25    | PASS / HTTP 200        |
| 14:54:55    | PASS / HTTP 200        |
| 14:55:25    | PASS / HTTP 200        |
| 14:55:39    | ECSタスク停止          |

ECSタスクの停止理由は `Task failed ELB health checks` だった。

アプリケーションがHTTP `200` を返せる状態になった後も、Healthy判定に必要な連続成功回数へ到達する前にタスクが停止していた。

同じデプロイで起動した他のタスクでも、類似するヘルスチェック結果が確認された。

### 4.3 原因分析

変更前のALBターゲットグループには、以下の設定が存在した。

```hcl
health_check {
  path                = "/login"
  matcher             = "200"
  interval            = 30
  timeout             = 5
  healthy_threshold   = 5
  unhealthy_threshold = 2
}
```

Spring Bootの起動直後には、ヘルスチェックへの接続が正常に完了しない時間帯が存在していた。

ALBターゲットの初回Healthy判定と、Unhealthy状態からの復帰判定では、必要なヘルスチェック成功回数が異なる。

新規登録されたターゲットは、最初のヘルスチェック成功によってHealthyと判定される場合がある。一方、Unhealthy状態からHealthy状態へ復帰するには、`healthy_threshold` で指定された回数の連続成功が必要となる。

今回のログでは、初期の `ConnectionReset` に続いて4回連続の `HTTP 200 PASS` が記録されたが、5回目の成功を確認する前にECSタスクが停止した。

このことから、Healthy状態への復帰に必要な連続成功回数が、デプロイ失敗に関係していた可能性が高いと判断した。

ただし、今回の調査ではHealthy判定のしきい値のみを変更した比較実験を実施したわけではない。また、観測したログだけではALBターゲットの全状態遷移を確定できない。

そのため、Healthy判定回数を単独の根本原因と断定するものではない。

## 5. 対応内容

### 5.1 Terraform設定変更

対象ファイル：

`terraform/runtime/alb.tf`

ALBターゲットグループのHealthy判定に必要な連続成功回数を変更した。

```diff
- healthy_threshold   = 5
+ healthy_threshold   = 2
```

ヘルスチェック間隔、タイムアウト、Unhealthy判定回数、およびECSヘルスチェック猶予期間は変更していない。

### 5.2 AWS環境再構築

Terraformの変更を含むAWS環境再構築を実施した。

再構築時には、以下を確認した。

- ECSサービスが安定状態になった。
- ALBターゲットがHealthyになった。
- ECSサービスの安定化待機が正常終了した。

## 6. 修正後の検証結果

検証日：2026年11月4日

### 6.1 GitHub Actions CD

修正後の環境で、GitHub Actionsから連続して2回のデプロイを実施した。

| 検証     | タスク定義 | 結果 | 実行時間 |
| -------- | ---------- | ---- | -------- |
| CD 1回目 | rev22      | 成功 | 1分32秒  |
| CD 2回目 | rev23      | 成功 | 4分26秒  |

どちらの実行でも、ECSサービスの安定化待機とデプロイ後のタスク定義検証が正常終了した。

### 6.2 ECSサービスの最終確認

AWS CLIの `describe-services` で以下を確認した。

| 項目              | 結果                         |
| ----------------- | ---------------------------- |
| Service Status    | ACTIVE                       |
| Task Definition   | equipment-inspection-task:23 |
| Desired Count     | 1                            |
| Running Count     | 1                            |
| Pending Count     | 0                            |
| Deployment Status | PRIMARY                      |
| Rollout State     | COMPLETED                    |

また、`list-tasks` により、RUNNING状態のタスクが1件であることを確認した。

なお、これらは2026年11月4日時点の修正後AWS環境における検証結果であり、その後の環境破棄や再構築後の状態を保証するものではない。

### 6.3 検証結果の評価

AWS環境再構築後、GitHub Actionsからのデプロイが2回連続で成功した。

この結果は、ALBヘルスチェックのHealthy判定回数を変更したことが、デプロイ安定性の改善に寄与したという仮説を強く支持する。

一方、環境再構築も同時に行っているため、他の条件による影響を完全には排除できない。

## 7. 今後の改善事項

- `/login` ではなく、アプリケーションの起動準備状態を判定できる専用のreadinessエンドポイントを検討する。
- ECSタスクの起動時間とALBヘルスチェック結果を継続的に確認する。
- デプロイ失敗時には、ECSサービスイベント、タスク停止理由、ALBログを時系列で照合する。
- Healthy判定回数やヘルスチェック猶予期間を変更する際は、アプリケーション起動時間を考慮する。

### Issue #9（今回の修正対応）

頻発するデプロイ障害への対応として、Issue #9で以下を実施した。

- ECSサービスイベントとALBヘルスチェックログの時系列分析
- ALBのHealthy判定回数の見直し（5回から2回）
- Terraform設定の修正
- AWS環境再構築による動作確認
- GitHub Actions CDの2回連続成功確認
- ECSサービスの安定稼働確認
- 本インシデントレポートの更新

今回の調査・修正・検証結果はIssue #9に集約する。

なお、readinessエンドポイントの導入など、今回実施していない追加改善は別途検討する。
