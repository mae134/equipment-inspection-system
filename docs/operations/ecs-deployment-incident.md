# ECS Deployment Incident Report

## 1. 概要

GitHub ActionsからAmazon ECSへアプリケーションをデプロイした際、
ALBのヘルスチェックに関連する問題により、ECSタスクが停止した。

その後、同じタスク定義を使用して手動で再デプロイしたところ、
正常に起動・稼働することを確認した。

根本原因は特定できておらず、継続調査の対象としている。

## 2. 対象環境

| 項目 | 内容 |
|---|---|
| アプリケーション | Equipment Inspection System |
| 実行環境 | Amazon ECS / AWS Fargate |
| ロードバランサー | Application Load Balancer |
| デプロイ | GitHub Actions |
| タスク定義 | `equipment-inspection-task:15` |
| コンテナポート | 8080 |
| ヘルスチェックパス | `/login` |
| ECSヘルスチェック猶予期間 | 90秒 |

## 3. 発生事象

GitHub Actionsから新しいタスク定義を使用したデプロイを実施した。

初回デプロイではECSタスクが停止し、
サービスは以前のタスク定義 `:14` に戻った。

## 4. 調査内容と確認結果

ALBヘルスチェックログをS3に出力し、レスポンスを確認した。

確認された主な結果は以下のとおり。

- 初期のヘルスチェックで `ConnectionReset` を確認した。
- その後、HTTP `200 PASS` のヘルスチェックも複数回確認した。
- `200 PASS` が記録されたにもかかわらず、初回デプロイのタスクは停止した。

なお、これらのログだけではタスク停止の根本原因を断定できない。

## 5. 復旧と検証

同じタスク定義 `equipment-inspection-task:15` を使用して
手動で再デプロイを実施した。

確認結果：

- ECSサービスが安定状態になった。
- ALBターゲットがHealthyになった。
- `https://kdevnest.com/login` へのHTTPリクエストで `200` を確認した。

手動再デプロイによる復旧は確認できたが、
GitHub Actionsからの再デプロイ成功を再検証したものではない。

## 6. 原因分析

### 確認できた事実

- 初回デプロイ時にALBヘルスチェック関連の失敗が発生した。
- 初期段階で `ConnectionReset` が記録された。
- その後 `200 PASS` も記録された。
- 同じタスク定義での手動再デプロイは成功した。

### 未確定事項

- 初回デプロイ時にタスクが停止した根本原因
- アプリケーション起動時間とヘルスチェック判定の関係
- ECSデプロイ設定が今回の事象に与えた影響

これらは仮説段階であり、原因として断定しない。

## 7. 今後の対応

GitHub Issue #127
「ECSデプロイ時のヘルスチェック安定性を改善する」で継続管理する。

今後の調査では、ECSサービスイベント、タスク停止理由、
アプリケーション起動ログ、ALBヘルスチェック結果などを
突き合わせて原因を分析する。

本ドキュメントの作成だけではIssue #127は完了としない。
